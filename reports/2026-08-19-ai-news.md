# 2026-08-19 AI 每日新聞

## 今日摘要

本日收錄 4 則官方／第一方消息。Claude Code 2.1.236 把跨 session 完成通知、預設模型與 sandbox 可靠度一起補強；Google 宣布把 Ask Gemini 帶進 Chat，讓搜尋資料、寫更新、生成圖片與排程集中在獨立 AI session；LiquidAI 釋出經量化感知蒸餾的 LFM2.5 Q4_0 模型；OpenAI 則讓早期客戶測試一種不交出底層內容、仍能偵測跨互動風險的 ZDR 安全處理方式。

## 重點新聞

### 1. Claude Code 2.1.236 加入跨 Session 閒置通知，也補強預設模型與 Sandbox

**發生什麼事**

Anthropic 發布 Claude Code 2.1.236。新版增加 `ANTHROPIC_DEFAULT_MODEL`，讓團隊或執行環境指定新 session 的起始模型；使用者在 `/model` 做的覆寫仍會保留。跨 session `SendMessage` 也新增 `notify_when_idle`，可以登記一次性的閒置通知，不必持續輪詢另一個 session 是否完成。

同一版也處理多個可靠度問題：sandbox 的 wildcard read-deny 在已允許目錄內仍會正確優先，重新命名檔案不能繞過限制；工作目錄被刪除後，剪貼簿、背景清理、local MCP log 與 skill hot reload 不再跟著失效。WSL 呼叫 `powershell.exe`、VS Code 螢幕閱讀器、自架 runner post-hook 與 burst SendMessage 也有修正。

**具體進步與限制**

多 session coding agent 現在能等到對方真正閒置才收到訊號，適合長時間 review、測試與修正分工。自動模式的 Git 檢查也不再因 `status.showUntrackedFiles=no` 而把含 untracked files 的工作樹誤判為乾淨。

`notify_when_idle` 目前只支援 macOS／Linux，而且是一次性通知；這不會替代測試、diff 檢查或任務失敗監控。新版改善的是協作、權限與執行可靠度，不代表 agent 產出的程式自動正確。

**對工作的影響**

- 前端團隊可把元件實作、視覺回歸與 code review 分給不同 session，只有對方完成時再接手。
- 共用 CI／開發容器可固定新 session 的預設模型，個人仍能依任務切換。
- 建議升級後回歸測試 wildcard deny、Git untracked 狀態、WSL 工具呼叫與長任務通知，並照常驗收 diff 與測試。

**日期證據：** Claude Code Changelog 的 2.1.236 明確標示 2026-08-19。

**產品狀態：** 已正式發布；跨 session 閒置通知目前限 macOS／Linux。

**官方來源：** [Anthropic：Claude Code Changelog](https://code.claude.com/docs/en/changelog)

**官方使用參考：** [Anthropic：Claude Code settings](https://code.claude.com/docs/en/settings)

### 2. Ask Gemini 將進入 Google Chat：搜尋、寫作與排程集中到獨立 Session

**發生什麼事**

Google 宣布在 Google Chat 加入 Ask Gemini 統一命令列。它能從 Gmail、Drive、Calendar 與 Chat 搜尋內容、追上討論、撰寫專案更新、生成圖片、安排會議與管理工作；每個需求會開在獨立 Gemini session，使用者可以在 Chat 內切換不同工作脈絡。

這不是 8 月 19 日已全面開放的功能。Google 預計自 8 月 26 日開始分批 rollout，初期只支援英文，並限 Business Standard／Plus、Enterprise Standard／Plus 與 Google AI Pro for Education 等符合資格的方案。

**具體進步與限制**

設計與工程協作常同時散在 Chat、Gmail、Drive 與 Calendar。Ask Gemini 把尋找決策、整理行動項目與建立後續工作拉回同一個協作介面，減少人工複製上下文。

介面遷移也有明確代價：Ask Gemini 會取代 Chat 現有 Gemini 側欄，Gems 暫時無法從這裡使用，側欄對話歷史不會自動搬到新介面。需要保留的紀錄要在 rollout 前自行匯出或下載，實際可見時間也會因網域 rollout 不同而有差異。

**對工作的影響**

- UI/UX 與前端可在 Chat 直接彙整需求、找 Drive 規格、起草站會更新與安排設計 review。
- 團隊應先定義哪些對話可被 AI 搜尋、引用如何驗證，以及生成圖片或建立任務後由誰負責驗收。
- 管理員要確認 Smart Features 與方案資格；使用者則應先匯出仍需保留的舊側欄對話。

**日期證據：** Google Workspace Updates 原始文章標示 2026-08-19。

**產品狀態：** 已宣布，預計 2026-08-26 起分批推出；初期英文限定。

**官方來源：** [Google Workspace Updates：Ask Gemini in Chat](https://workspaceupdates.googleblog.com/2026/08/ask-gemini-in-chat.html)

**官方使用參考：** [Google Chat Help：Get started with Ask Gemini in Google Chat](https://support.google.com/chat/answer/17036303)

### 3. LFM2.5 推出 QAD 4-bit 模型：維持 Q4_0 速度，少掉常見品質損失

**發生什麼事**

LiquidAI 釋出 LFM2.5-230M、350M、1.2B-Instruct 與 2.6B 的 QAD Q4_0 GGUF。QAD 是 quantization-aware distillation：模型在蒸餾時就學習 4-bit 量化後會出現的誤差，目標是在維持 Q4_0 記憶體與推論速度的同時，保留更多 BF16 品質。

官方以五次重複測試報告，四個尺寸平均找回一般 Q4_0 相對 BF16 所損失準確度的約 97%。230M／350M 在測試裝置上比部分較高品質量化快 4–33%，1.2B／2.6B 則快 3–14%，並在評估誤差內接近 Q5_K_M 或 Q4_K_M 品質。

**具體進步與限制**

這批模型可直接以 GGUF／llama.cpp 使用，讓小型本機功能少一點「速度夠但回答明顯退步」的取捨。官方同時在 MacBook Pro、迷你電腦、Galaxy S26 Ultra 與 Raspberry Pi 5 展示結果，比只提供桌機 GPU benchmark 更接近邊緣部署情境。

不過 97% 是廠商在指定評估集上的平均結果，不是所有語言、工具呼叫與產品任務都會等比例改善；不同 CPU、記憶體頻寬、context 長度與 runtime 仍會改變體感。

**對工作的影響**

- 前端可先用它原型化離線搜尋、表單輔助、內容分類與隱私敏感的本機 agent。
- 1.2B Q4_0 約 696 MB，適合先在桌面或高階行動裝置測試，再決定是否下放到更小硬體。
- 驗收應包含繁中品質、首字延遲、每秒 token、記憶體與電量，並保留不支援裝置的雲端 fallback。

**日期證據：** LiquidAI 在 Hugging Face 發布的 Team Article 標示 2026-08-19。

**產品狀態：** QAD Q4_0 GGUF 已公開，可用 llama.cpp 執行。

**第一方來源：** [LiquidAI：Compressing LFM2.5 Models Using QAD](https://huggingface.co/blog/LiquidAI/qad)

**第一方使用參考：** [LiquidAI：LFM2.5-1.2B-Instruct-GGUF model card](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct-GGUF)

### 4. OpenAI 測試 Private Safety Processing：ZDR 客戶可跨互動找風險，不交出內容

**發生什麼事**

OpenAI 公布 Private Safety Processing 早期客戶預覽。符合 Zero Data Retention（ZDR）的 API 客戶可讓提示與回覆在處理後不被保留，但這也讓跨多次互動才浮現的風險模式較難被辨識。新方法把相關互動的安全分析放在客戶控制的基礎設施，或存放在由客戶金鑰加密、OpenAI 人員無法直接閱讀的環境。

OpenAI 接收的是有限安全訊號，而不是底層內容；官方表示這些訊號可用來提醒客戶或執行預先同意的動作。此設計希望同時保留 ZDR 的隱私邊界與長期濫用偵測能力。

**具體進步與限制**

以前要做跨互動安全分析，常意味著供應商必須保留更多提示、回覆或人工審查權限。Private Safety Processing 嘗試把內容保管、解密權與供應商安全訊號拆開，讓敏感工作流不必用「完全沒有跨互動偵測」換取零資料保留。

這仍是早期客戶測試。OpenAI 預計 9 月公布白皮書與後續 rollout，資格、支援端點、誤判處理與例外條款仍需等正式文件。ZDR 也不是所有 API 功能都天然相容，例如部分背景處理、工具與第三方 MCP 仍有各自的儲存條件。

**對工作的影響**

- 處理內部設計稿、原始碼或客戶資料的 AI 產品，可先把內容流向、金鑰與安全事件責任拆清楚。
- 前端需為風險警示、被阻擋操作與申訴設計可理解的狀態，不能只顯示模糊錯誤。
- 正式採用前應逐端點確認 ZDR 相容性，並把第三方工具、檔案與 MCP 的資料政策納入威脅模型。

**日期證據：** OpenAI 原始文章標示 2026-08-19。

**產品狀態：** Private Safety Processing 正由早期客戶測試，尚未普遍開放；白皮書與 rollout 預計 9 月公布。

**官方來源：** [OpenAI：Offering Zero Data Retention for frontier models](https://openai.com/index/offering-zero-data-retention-for-frontier-models/)

**官方使用參考：** [OpenAI API：Data controls in the OpenAI platform](https://platform.openai.com/docs/models/default-usage-policies-by-endpoint)

## 對工作流的意義

今天的共同主題是「AI 工作流開始補齊長時間協作、跨工具上下文、本機部署與隱私安全」。Claude Code 讓多 session coding 工作比較不需要人工盯著；Ask Gemini 把協作資料與下一步動作拉回 Chat；LiquidAI 降低本機 4-bit 模型的品質取捨；OpenAI 則嘗試把跨互動安全偵測與內容保管權分離。對前端與設計團隊而言，真正值得驗收的不只是功能能不能跑，而是通知是否準確、來源能否追溯、低階裝置是否可用，以及資料在每個邊界究竟由誰控制。
