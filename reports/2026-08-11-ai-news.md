### 1. GitHub Copilot for JetBrains 加入跨 session 記憶、Ollama 與 Codex 工作流整合

**發生什麼事**

GitHub 更新 JetBrains IDE 的 Copilot 外掛。Copilot Memory 可把 repository 事實與使用者偏好留給之後的 session 使用；Bring Your Own Key（BYOK）則可連到本機 Ollama 模型。外掛也補上 Codex 對話記錄、instructions 與 skills 支援，並能偵測與協助安裝 Copilot CLI。這次同時改善 agent session 恢復、思考內容呈現與多項穩定性問題。

**具體進步與限制**

過去換一個對話，常要重新交代專案規則、命名慣例與工作偏好；現在記憶可在同一 repository 的不同 session 間重用，並附來源引用供使用者檢查或刪除。Ollama 讓團隊能在 JetBrains 內使用自管模型，不必把每個工作都送到預設雲端模型；Codex 的 skills 與 instructions 也可直接延續既有自動化規範。

Copilot Memory 仍是 public preview，且要使用付費 Copilot 方案；組織管理員可以停用。BYOK 不等於模型一定離線或符合公司政策，仍須檢查所選模型、Ollama 主機與資料流向。

**對工作的影響**

- 前端工程師可把框架版本、測試命令、設計 token 與 API 約定留成有引用的 repository 記憶，減少每次對話重述，但仍要把真正不可違反的規則放在版本控制的 instructions／skill 中。
- WebStorm、IntelliJ 等 JetBrains 使用者可用 Ollama 做低風險草稿、分類或局部重構，再把需要更強推理的工作切回雲端模型；導入前應測量速度、品質與資料治理。
- UI/UX 可參考「記憶有來源、可檢視、可刪除、可由管理員關閉」的互動，不要把 AI 長期記憶做成不可追溯的黑盒。

**日期證據：** GitHub Changelog 頁面標示「August 11, 2026」。

**產品狀態：** JetBrains 外掛更新已提供；Copilot Memory 為 public preview，實際功能仍受方案、外掛版本與組織政策限制。

**官方來源：** [GitHub Changelog：Copilot memory and Ollama in GitHub Copilot for JetBrains](https://github.blog/changelog/2026-08-11-copilot-memory-and-ollama-in-github-copilot-for-jetbrains/)

**官方使用參考：** [GitHub Docs：About Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)、[JetBrains Marketplace：GitHub Copilot versions](https://plugins.jetbrains.com/plugin/17718-github-copilot--your-ai-pair-programmer/versions)

### 2. MAI-Code-1.1-Flash 正式進入 GitHub Copilot，速度、成本與圖片理解同步改善

**發生什麼事**

Microsoft 發布 MAI-Code-1.1-Flash，並於同日把它加入 GitHub Copilot。新模型可讀取圖片，針對寫程式、遵循指令與工具使用做了強化；Microsoft 表示，相較前一版，其串流速度提高約 25%、完成工作使用的 token 減少約 25%，定價降到約四分之一。GitHub 對 Copilot 年繳訂閱者以 0.25 倍 premium request multiplier 計算，Free 與 Student 可透過 Auto model selection 使用，付費方案則可手動選取。

GitHub 也同日宣布舊版 MAI-Code-1-Flash 將於 2026-09-10 自 Copilot 退場，企業管理員需確認新模型政策是否已開啟。

**具體進步與限制**

圖片輸入讓使用者能把錯誤畫面、設計稿或 UI 截圖一起交給 coding agent，不必先手動轉成文字。Microsoft 的產品遙測顯示，CLI 任務完成率提升 22%、.NET agentic coding 提升 15%，生成程式碼一週後仍保留的比例增加 4%，使用者回訪增加 9%。這些是 Microsoft 自家產品與線上實驗數據，不能直接當成所有語言、repo 與任務都會有相同比例的保證。

**對工作的影響**

- 前端工程師可用「截圖＋元件程式碼＋驗收條件」測試版面修正、錯誤排查與視覺比對，並把 0.25 倍額度模型留給高頻、短迭代工作。
- 團隊可用真實 issue 做 A/B：比較一次成功率、測試通過率、token 與人工修正時間，再決定是否把 Auto selection 或預設模型切過去。
- Copilot Business／Enterprise 管理員應在 9 月 10 日前啟用替代模型並通知成員，避免固定選用舊模型的流程突然失效。

**日期證據：** Microsoft AI 與 GitHub Changelog 的新模型頁面均標示「August 11, 2026」；退場公告也於同日發布。

**產品狀態：** MAI-Code-1.1-Flash 已在 GitHub Copilot 正式提供；方案、client 與管理員 policy 會影響可用性。

**官方來源：** [Microsoft AI：MAI-Code-1.1-Flash — Better, faster, at a quarter of the cost](https://microsoft.ai/news/mai-code-1-1-flash-br-better-faster-at-a-quarter-of-the-cost/)、[GitHub Changelog：MAI-Code-1.1-Flash available in GitHub Copilot](https://github.blog/changelog/2026-08-11-mai-code-1-1-flash-available-in-github-copilot/)、[GitHub Changelog：Upcoming deprecation of MAI-Code-1-Flash](https://github.blog/changelog/2026-08-11-upcoming-deprecation-of-mai-code-1-flash/)

### 3. Claude Code 2.1.228 修好跨 session 與 Windows 問題，並收緊雲端同步 skill 的安全邊界

**發生什麼事**

Anthropic 發布 Claude Code 2.1.228。新版修正少見的終端介面重繪凍結、Windows 上 Git 與 Git Bash 偵測、`/tui` 意外恢復舊模型、跨 session inbox 訊息、Remote Control `/resume` 顯示錯誤歷史、self-hosted runner checkout hook，以及清理 session 時誤刪 project memory 內容等問題。

最重要的安全調整是：從 claude.ai 同步的 skills 不能再蓋過本機 slash commands 或 MCP prompts；其描述會被清理並標示為非可信內容，skill body 也不能執行 `!` shell command 或展開 `@` 檔案。

**具體進步**

跨 session 訊息、背景 task 後的 session 銜接與 Remote Control 歷史變得更可靠，減少代理完成工作後找不到結果或混入別段對話的情況。雲端同步 skill 則從「可影響本機命令解析」改成受限輸入，降低同名覆蓋、提示注入與未預期本機讀檔／執行命令的風險。新版也改善 compaction 倒數、停滯提示、Vertex 驗證失敗速度與 Write tool 行為一致性。

**對工作的影響**

- 使用 Windows、Remote Control 或 self-hosted runner 的前端團隊可優先更新，並以「恢復 session、接收跨 session 訊息、checkout 後執行測試、保留 project memory」做回歸檢查。
- 專案級安全規則與可執行工作流應維持在受版本控制的本機／repository skill；雲端同步 skill 適合當方便的文字指引，不應假設它具有同等命令權限。
- UI/UX 可參考來源分級：同步內容必須被標示、限制能力並避免無聲覆蓋本機項目，讓使用者知道哪一層設定正在生效。

**日期證據：** Anthropic Claude Code Changelog 的 2.1.228 節標示「August 11, 2026」。

**產品狀態：** 已正式發布。

**官方來源：** [Anthropic Claude Code Changelog](https://code.claude.com/docs/en/changelog)

### 4. OpenAI Daybreak 模型上架 Amazon Bedrock，但只開放經審核的防禦性資安用途

**發生什麼事**

OpenAI 將 Daybreak Blue 與 Daybreak Red 模型帶到 AWS。Blue 是包含 GPT-5.6 Sol 的通用前沿模型系列，搭配面向防禦者的資安 safeguards；Red 則針對獲授權的漏洞研究、exploit validation 與安全測試做專門訓練。合格且通過 Daybreak Access 審核的客戶，可從 Amazon Bedrock console 或透過 `bedrock-mantle` 使用 Responses API 介面呼叫。

**具體進步與限制**

企業可把高能力資安模型放進既有 AWS 身分、權限與監控環境，不必另外建立一套模型供應鏈。Red 的專門能力也讓防禦團隊能在有授權的環境內做更深入的驗證。

這不是一般開發者可直接啟用的公開模型。申請者需提供組織、專業用途與身分資料，維持 SSO、MFA、RBAC、API key 治理與使用紀錄；只允許擁有、營運或已獲明確授權的系統，且不可把 Daybreak Access 轉供外部客戶。

**對工作的影響**

- 有正式 AppSec／紅隊流程的前端團隊，可把依賴漏洞驗證、授權測試與修補建議接到既有 Bedrock 環境；一般 UI 開發不應把它當日常 coding 模型。
- 安全工具介面需要顯示目標授權、作用範圍、模型版本、執行紀錄與人工核准，不能把高風險動作藏在單一步驟 agent 後面。
- 導入前要先確認公司是否符合 Daybreak Access 與 AWS Bedrock 條件，再估算治理與稽核成本；「已上架 AWS」不等於所有 AWS 帳號立即可用。

**日期證據：** OpenAI 官方文章標示「August 11, 2026」。

**產品狀態：** 已在 Amazon Bedrock 提供，但限經 Daybreak Access 審核的合格企業與資安人員。

**官方來源：** [OpenAI：Daybreak models are now available on AWS](https://openai.com/index/daybreak-models-are-now-available-on-aws/)

**官方使用與限制參考：** [OpenAI：Request Daybreak Access](https://openai.com/form/enterprise-trusted-access-for-cyber/)、[AWS Docs：OpenAI model cards for Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards-openai.html)

### 5. IBM Research 展示精簡型 agent 記憶：ALTK-Evolve 用較少 token 保留可重用規則

**發生什麼事**

IBM Research 在 Hugging Face 發布企業技術文章，比較 ACE 與開源的 ALTK-Evolve。兩者都從 agent 執行軌跡中抽出可重用經驗，但 ALTK-Evolve 不把整份 playbook 全塞回 prompt，而是先依當前任務選出相關 guidelines。IBM 以 AppWorld 測試指出，DeepSeek-V3.2 搭配 ALTK-Evolve 的完成率為 89.3／80.4，所用 memory token 約 263K；ACE 為 80.4／73.2、約 634K。gpt-oss-120b 的結果較接近，但 ALTK-Evolve 使用 116K memory token，ACE 為 777K。

**具體進步與限制**

精進點不只是「讓 agent 記更多」，而是把記憶生成與取用拆開：離線從成功、失敗軌跡整理規則，執行時只帶入與眼前任務最相關的部分。這能降低長 prompt 成本，也減少過多舊規則干擾決策。專案提供 Python 安裝、範例、demo、MCP server，以及 Claude Code／Codex 的快速入門，可供實際驗證。

報告數字來自 IBM 的單次 pass@1 controlled runs，ACE 也是 IBM 自行執行的比較；文章也表示弱模型的正確率差異落在 run-to-run noise 範圍。這些結果適合當工程假設，不應直接當成跨資料集的普遍結論。

**對工作的影響**

- AI coding 工作流可把 code review 修正、測試失敗原因與設計系統違規整理成可選取的 guidelines，避免每次把整份歷史紀錄塞進 prompt。
- 前端團隊應同時量測任務成功率、memory token、延遲與錯誤規則命中率；如果只看 benchmark 分數，可能忽略記憶選錯所造成的回歸。
- UI/UX 可提供「本次使用哪些記憶、來源是哪次軌跡、為何被選入」的可視化，讓長期自我改進仍可追蹤與撤回。

**日期證據：** Hugging Face Enterprise Article 頁面標示「Published August 11, 2026」，作者列為 IBM Research 團隊。

**產品狀態：** 研究與開源實作已公開；benchmark 為第一方實驗結果，不是通用產品 SLA。

**第一方來源：** [IBM Research on Hugging Face：Self-Improving Agents with ALTK-Evolve](https://huggingface.co/blog/ibm-research/altk-evolve-sldd)

**實作與論文參考：** [GitHub：AgentToolkit/altk-evolve](https://github.com/AgentToolkit/altk-evolve)、[arXiv：Trajectory-Informed Memory Generation for Self-Improving Agent Systems](https://arxiv.org/abs/2603.10600)

### 6. GitHub Copilot 用量報表可拆出各模型的輸入、輸出與快取 token

**發生什麼事**

GitHub 更新 Copilot usage report：每個模型的 AI credits 除了總量，現在還可分成 `input`、`output`、`cache_read` 與 `cache_write` token。報表提供給 Copilot Business／Enterprise 管理員，也開放個人 Copilot 使用者查看。

**具體進步**

過去只能看到較粗的用量與費用，難以判斷成本是來自過長輸入、模型輸出、未命中快取，或建立快取。現在可依使用者、模型與日期找出差異，讓團隊以實際資料調整模型、context、prompt 與工作分派。官方 billing report 最多可選 31 天，日期欄位以 UTC 計算，因此與台灣工作日彙總時需要先做時區轉換。

**對工作的影響**

- 前端團隊可分辨「把整個 repo 都丟進 prompt」和「真正需要長輸出」各自造成的成本，再針對高 input token 任務縮小檔案範圍。
- 導入 prompt caching 或長期 agent session 時，可觀察 cache read/write 比例是否真的降低總花費，而不是只增加建立快取的成本。
- 管理介面可把成本拆成可採取行動的原因，但不要拿 token 多寡直接當工程師績效；複雜任務與模型定價本來就不同。

**日期證據：** GitHub Changelog 頁面標示「August 11, 2026」。

**產品狀態：** 已正式提供給符合條件的 Copilot 個人使用者與 Business／Enterprise 管理員。

**官方來源：** [GitHub Changelog：Per-model token breakdown in the usage report](https://github.blog/changelog/2026-08-11-per-model-token-breakdown-in-the-usage-report/)

**官方使用參考：** [GitHub Docs：Billing reports](https://docs.github.com/en/billing/reference/billing-reports)

### 7. ChatGPT Ads 擴大到英國、墨西哥、巴西、日本與南韓

**發生什麼事**

OpenAI 在既有 ChatGPT 廣告測試頁加入 8 月 11 日更新：ChatGPT Ads 已擴大到英國、墨西哥、巴西、日本與南韓。廣告會與回答分開、清楚標示，廣告主不能存取使用者對話；使用者可關閉個人化、刪除廣告資料並解釋為何不想再看到某則廣告。OpenAI 也開放 Ads Manager 入口，讓廣告主建立 campaign、設定預算與目標、批次上傳素材並查看分析。

**具體進步與限制**

這次不是新廣告格式，而是從既有測試擴到五個新市場，亞洲包含日本與南韓。它讓品牌能在對話式探索場景測試素材與成效，也把「回答內容」和「付費曝光」的責任邊界做成介面規則。

原頁最初於 2 月發布，本日合格事件僅是頁面明確標示的五國擴張，不把 2 月的美國測試重算成新消息。此功能仍屬測試，實際方案、廣告量與市場覆蓋可能持續調整。

**對工作的影響**

- UI/UX 與前端可觀察對話結果中如何固定呈現「Sponsored」標示、控制個人化與說明推薦原因，避免商業內容混成模型答案。
- 平面與品牌設計可為日本、南韓等市場準備語言、文化與尺寸版本，並用 Ads Manager 的 campaign 分組測試，而不是直接複製同一套英文素材。
- 產品團隊應把關閉個人化、刪除資料、回報不相關廣告與廣告落地頁揭露納入完整流程，並持續檢查各地法規與實際投放資格。

**日期證據：** OpenAI 官方頁面上方標示「August 11, 2026」，更新段落明確寫明 ChatGPT Ads 已在上述五國推出；頁面同時保留原始 2 月測試背景。

**產品狀態：** 測試中，為新市場擴張而非全面正式上線。

**官方來源：** [OpenAI：Testing ads in ChatGPT](https://openai.com/index/testing-ads-in-chatgpt/)

## 對工作流的意義

今天的主線是讓 agent 從「一次性聊天」走向可管理的長期工作系統：Copilot Memory 與 ALTK-Evolve 都在處理跨任務記憶，但一個強調產品內的引用與控制，另一個強調只取回相關規則以節省 token；Claude Code 則把同步 skill、跨 session 與遠端操作的安全邊界補得更清楚。MAI-Code-1.1-Flash 和 Copilot token 報表讓團隊能用速度、成功率與實際輸入／輸出成本選模型。對前端、UI/UX 與平面設計而言，下一步不是盲目增加 AI 功能，而是讓記憶有來源、成本可分解、遠端動作可驗證、廣告與回答有明確分界，並對受限模型與自家 benchmark 保留清楚的資格和證據說明。
