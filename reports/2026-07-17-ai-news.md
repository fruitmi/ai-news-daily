2026-07-17 整理 4 則值得追蹤的 AI 更新：GitHub 把 Copilot 的程式審查規則、執行環境、手機修正與成效量測做得更可控，OpenAI 則提出以成功工作而非 token 數量衡量 AI 投資。當日官方產品消息集中在 GitHub；其餘沒有用 Google 的週摘要或 Canva 前幾日發布來湊數。

## 重點新聞

### 1. GitHub Copilot 程式審查可在功能分支測規則，並獨立配置環境與網路

Copilot code review 現在會從 Pull Request 的 head branch 讀取審查規則，團隊可在合併前測試 `AGENTS.md`、`copilot-instructions.md` 與 skills。它也新增 `REVIEW.md`、`GEMINI.md`、`CLAUDE.md` 支援、專用 `copilot-code-review.yml` 準備步驟、預設啟用的網路防火牆，以及與 cloud agent 分開的 runner 設定。

- 具體進步：審查規則不必先進入主分支才能驗證，依賴安裝、測試工具與網路權限也能針對 code review 單獨管理，減少錯誤規則影響所有 PR，或 agent 因環境不足而給出空泛建議的情況。
- 工作影響：前端團隊可在功能分支加入元件命名、設計 token、無障礙、瀏覽器相容性與測試要求，再讓 Copilot 依同一分支內容審查；若需要安裝 lint、型別或視覺測試工具，可放進專用 setup，但仍要限制外網、保護 secrets，並由人工確認建議。
- 當日官方來源：[GitHub Changelog](https://github.blog/changelog/2026-07-17-copilot-code-review-customization-and-configurability-improvements/)
- 操作參考：[GitHub Docs：About GitHub Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review)

### 2. GitHub Mobile 可從 PR 審查留言一鍵交給 Copilot 修正

最新版 GitHub Mobile 在 Pull Request 主畫面與個別 Copilot code review 留言加入 **Fix with Copilot**，點一下即可讓 cloud agent 著手處理意見，不必先手動整理提示。功能已在 iOS 與 Android 正式版提供。

- 具體進步：離開電腦時也能把明確的 review comment 直接轉成修正任務，省下複製留言、重述問題與另開 agent 工作階段的步驟，讓小型修正更快進入可檢查的 PR 流程。
- 工作影響：前端工程師可在手機上先處理文案、樣式、型別或測試缺漏等清楚意見，回到桌面後再檢查 diff、跑瀏覽器與視覺測試；涉及架構、資料安全或模糊 UX 判斷的留言仍不適合一鍵接受。
- 當日官方來源：[GitHub Changelog](https://github.blog/changelog/2026-07-17-github-mobile-fix-pull-request-comments-with-copilot-cloud-agent/)
- 操作參考：[GitHub Docs：Use Copilot cloud agent on GitHub Mobile](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-mobile)

### 3. GitHub Copilot 指標可看每個 repo 的 agent 與 code review 活動

Copilot usage metrics REST API 的 repository-level 報告正式上線，可按日查看各 repo 中 coding agent 建立與合併的 PR、code review 審過的 PR 與建議類型。同日另一項更新也把 Copilot app 的活躍使用者、session、request、prompt 與 token 用量加入組織和企業報告，因此合併為同一則，不重複計數。

- 具體進步：管理者不再只能看組織或個人總量，現在能找出 Copilot 真正在哪些程式庫產生 PR、審查與 app 使用，並把採用狀況和需要培訓或調整規則的 repo 對上。
- 工作影響：前端主管可把每日 repo 報告接進內部儀表板，比較 agent PR 合併率、review 建議與 app 用量，再搭配測試通過率、回滾、缺陷和人工修改量判斷價值；不要只用 prompt、token 或 PR 數量當成生產力。
- 當日官方來源：[Repository-level metrics GA](https://github.blog/changelog/2026-07-17-repository-level-github-copilot-usage-metrics-generally-available/)
- 同日官方來源：[Copilot app metrics](https://github.blog/changelog/2026-07-17-github-copilot-app-now-available-in-the-usage-metrics-api/)
- API 範例：[GitHub Docs：Copilot usage metrics REST API](https://docs.github.com/en/rest/copilot/copilot-usage-metrics)

### 4. OpenAI 建議用成功工作與人工修正成本衡量 AI，而不是只算 token

OpenAI 提出 **Useful Intelligence per Dollar** 評估框架，主張 AI 投資應追蹤完成了多少有用工作、每個成功任務的完整成本、結果是否可直接使用，以及規模擴大後價值是否成長。完整成本要包含重試、延遲、人工複核與返工，不只看每 token 價格。

- 具體進步：這套框架把模型比較從單次 benchmark 或便宜 token，改成 `ready to use`、`needs correction`、`needs escalation` 三種實際結果，讓團隊能看出較強模型是否因少重試、少人工修改而反而更省。
- 工作影響：前端與設計團隊可先替一條工作流定義 done，例如程式修改需通過測試、UI 草稿需符合元件與無障礙規則，再記錄一次可用率、人工修正時間與升級處理比例。這是 OpenAI 提出的管理框架，不是獨立第三方 benchmark，仍需用自家專案驗證。
- 當日官方來源：[OpenAI：A scorecard for the AI age](https://openai.com/index/a-scorecard-for-the-ai-age/)

## 對工作流的意義

今天的共同方向是讓 AI coding 從「能不能產生內容」走向「規則能否測試、執行環境是否受控、修改是否能快速交辦、成效是否可被驗證」。前端與設計團隊可以先把審查要求寫進 repo、替 agent 限制網路與工具，再以測試通過、人工修正與回滾等結果衡量實際價值，而不是只看 prompt 或產出數量。
