## 重點新聞

### 1. GitHub Copilot 強化 JetBrains agent 工作流，MCP、自訂 agent 與觀測設定一次到位

GitHub Copilot 的 JetBrains 外掛已更新，Claude agent 流程現在可直接使用 MCP server 與自訂 agent。團隊也能在 IDE 內設定 OpenTelemetry、BYOK／自訂端點的輸入與輸出 token 上限，以及是否啟用內建模型；Copilot CLI 同步加入工作階段分叉、`/rubber-duck` 複核與待辦清單。

- 具體進步：原本分散在不同工具或需靠外部設定處理的 agent 工具、觀測、成本上限與模型管理，現在集中到 JetBrains Copilot 設定與工作流程裡。MCP 診斷、問答提示通知、model picker、路徑大小寫與 session recording 也一併改善，減少 agent 卡住時反覆猜設定、重開工作階段或人工整理進度。
- 工作影響：使用 WebStorm、PhpStorm 或 IntelliJ 的前端團隊，可把設計系統檢查、測試、文件與安全檢查做成 repo 專用 agent，再用 MCP 接 issue、資料庫或內部工具；OpenTelemetry 可追蹤 agent 執行時間與失敗點，token 上限則避免 BYOK 或自訂模型無限制消耗。
- 導入注意：功能需要最新版 GitHub Copilot for JetBrains 外掛。先在非正式分支驗證 MCP 可讀取的資料、命令核准、模型可用性與遙測資料範圍，再把設定推向團隊。

### 2. GitHub 將 Copilot App 與 cloud agent 納入統一企業政策，不同開發入口不再各管各的

GitHub 的企業管理設定現在涵蓋 Copilot App 與 Copilot cloud agent，與既有的 Copilot CLI、VS Code 共用 `managed-settings.json`。企業可集中限制外掛與 marketplace、禁止略過核准提示，並指定新對話預設使用自動選模；Copilot App 也新增獨立存取政策，不再跟著 CLI 開關一起啟用或停用。

- 具體進步：團隊不必再為桌面 App、IDE、CLI 與雲端 agent 各維護一套規則。同一份企業設定會優先於開發者本機選項，更新後約一小時內、重新啟動或重新登入時套用；App 存取可選全企業啟用、全企業停用或交由組織決定，讓工具可用性與 agent 權限分開治理。
- 邊界差異：cloud agent 會套用外掛與 marketplace 等適合背景任務的規則；是否允許略過互動核准只影響 Copilot App、CLI 與 VS Code 等互動式客戶端，不應誤以為所有入口的核准模型完全相同。
- 工作影響：前端與設計系統團隊可先核准必要的 MCP／外掛與 marketplace，把會執行指令、讀檔或抓網址的動作保留人工核准，再讓 App、VS Code、CLI 與 cloud agent 使用一致邊界。管理員應先盤點目前 CLI 政策，因 Copilot App 專用政策預設為 Enabled everywhere。

- 同日政策更新：[GitHub Changelog：Manage GitHub Copilot app access with a dedicated policy](https://github.blog/changelog/2026-07-27-manage-github-copilot-app-access-with-a-dedicated-policy/)

### 3. OpenAI 研究：設計師最常用 AI 跨出原職能，工程與行銷工作也在跨部門流動

OpenAI 分析超過 80 萬則美國 ChatGPT 使用者的工作訊息後發現，16.8% 的工作相關訊息涉及使用者原職業之外的任務；排除寫作、摘要等通用工作後，43.5% 的職業特定訊息屬跨職能。設計使用者特別明顯：在職業特定訊息中，有 75% 對應其他職能的任務。

- 具體進步：這份研究沒有推出新功能，而是把「AI 讓誰開始做哪些原本要交接的工作」量化。設計使用者的全部工作訊息中約 35.2% 涉及其他職業，常見流向包含工程與行銷；工程任務也廣泛出現在其他職業。這讓團隊可用實際任務與交接點規劃 AI，而不是只用節省時間或生成數量衡量採用。
- 工作影響：UI/UX 與平面設計師可先用 AI 做前端除錯、資料分析或行銷素材初稿，工程師也能先整理產品訊息與 demo，但跨職能不等於取代專業審核。實務上應把資料來源、可修改範圍、品牌與無障礙標準、技術驗證和最後負責人寫進 brief。
- 解讀限制：研究來自美國 ChatGPT 使用資料，職業是推估結果，且訊息分類不等於完成品質或實際產值；比例適合用來找值得測試的交接流程，不適合直接當成裁員或組織重整依據。
- 當日官方來源：[OpenAI：How AI is expanding what people do at work](https://openai.com/index/how-ai-is-expanding-what-people-do-at-work/)
- 完整研究：[Work at the Frontier report](https://cdn.openai.com/pdf/work-at-the-frontier-report.pdf)

## 對工作流的意義

今天的共同訊號不是再多一個聊天入口，而是 agent 開始需要可觀測、可限制、跨入口一致的工作邊界，同時人也在把原本要交給別職能的任務先做一版。前端與設計團隊可以先挑一條真實交接流程：定義 agent 可用工具、token 與核准規則，記錄執行時間和失敗點，再由原本負責的工程、設計或行銷角色做最終審核。這比只看產出數量，更能判斷 AI 是否真的減少等待與重工。
